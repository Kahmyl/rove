# ADR: File artifact authority for browser uploads

Date: 2026-09-07

Status: accepted and implemented

## Decision

Browser upload accepts opaque, session-scoped Rove `file` evidence IDs. It does
not accept host filesystem paths.

Rove provides two explicit ways to create those artifacts:

1. `evidence.create_file` materializes bounded content already supplied by the
   agent. The request contains a leaf filename, MIME type, encoding, and bytes;
   there is no path field. Generated content is limited to 512 KiB.
2. `evidence.request_file_grant` asks the user to select existing files through
   the native Rove Companion picker. The picker is the consent boundary. The
   agent supplies only a human-visible reason and whether multiple selection is
   required. Selected paths stay inside Companion and are never returned.

The Runtime stores the bytes as `file` evidence and records filename, MIME
type, size, SHA-256 digest, source, and (for user selections) an opaque grant
ID. It does not persist the source path in evidence or observations. A user
grant is limited to 64 MiB per file and 100 files per request.

## Why

The browser engine already supports direct file inputs and visible controls
that emit a dynamic file chooser. The missing boundary was not browser
perception: a fresh agent task could create a file on the host but could not
turn that path into authorized upload evidence.

Adding a raw `path` argument would make browser upload an unrestricted local
file-read and exfiltration primitive. Treating agent-generated bytes and
pre-existing user files as the same authority would also hide the human consent
decision.

## Flows

### Agent-generated artifact

1. The agent calls `evidence.create_file` with content and a leaf filename.
2. MCP validates encoding, filename, and decoded byte size.
3. Runtime persists raw bytes and provenance as session-scoped file evidence.
4. The returned `ev_...` ID is supplied to `browser.interact` with `kind:
"upload"`.

### Existing user file

1. The agent calls `evidence.request_file_grant` with a human-visible reason.
2. Companion brings forward Rove and opens the operating-system file picker.
3. Cancellation returns `{ status: "cancelled", evidence: [] }` and creates no
   artifacts.
4. Selected bytes travel directly from Companion to the loopback Runtime.
   Paths do not travel through MCP or the control plane.
5. Runtime returns opaque evidence metadata to the agent.

## Invariants

- No MCP file-artifact tool accepts a filesystem path.
- A chooser-opening web control is grounded by its advertised `activate`
  capability; `upload` is the interaction mechanism, not a guessed target
  capability.
- Only `file` evidence with a binary payload can be used for upload.
- Grant cancellation is non-consequential and creates no artifact.
- Evidence and observation metadata contain no selected local path.
- Runtime independently enforces byte limits even when an upstream component
  has already validated the request.

## Deferred extensions

- Explicit directory/workspace grants with revocation and durable scope.
- Chunked agent-generated artifacts larger than the control-plane command
  envelope.
- Directory upload and recursive manifest evidence.

These extensions must preserve the same opaque-ID and explicit-consent model.
