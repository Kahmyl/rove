# Workflow Portability Decision

**Status:** Decision accepted and implementation qualified deterministically. Supabase Auth plus Postgres/RLS is the selected provider; deployment-backed qualification remains required before synchronization is enabled for users.

## Accepted decision

Rove uses personal Supabase Auth identities with Google sign-in and email OTP, independently of Codex/ChatGPT identity. The Supabase project belongs in Frankfurt and remains on Supabase Free during the private exploratory period. There are no organizations, teams, shared Workflow owners, invitations, or enterprise tenancy.

This decision does not authorize cloud task history, results, artifacts, screenshots, recordings, downloads, browser profiles, credentials, local paths, approvals, or execution state. Those remain device-local.

## Provider and operating posture

Supabase Auth plus one Postgres schema protected by grants and row-level security is the selected narrow boundary. Desktop contains only the publishable project key and user session. Account deletion uses a narrowly scoped authenticated-subject database function, so no service-role secret or additional hosted runtime is introduced. Free-plan inactivity and availability are truthful unavailable states, not reasons to block device-local use or introduce paid infrastructure. See the official [Auth](https://supabase.com/docs/guides/auth), [row-level security](https://supabase.com/docs/guides/database/postgres/row-level-security), and [pricing](https://supabase.com/pricing) documentation.

Before adoption, prove authenticated owner isolation, denied anonymous access, conditional revisions, operation idempotency, tombstone retention, stale-client non-resurrection, export/account deletion, region selection, token storage/logout behavior, inactivity behavior, quotas, and recovery from provider outage. Use only the portable schema already validated in the application.

## Engineering completed

`workflow-portability.ts` defines and validates the only portable projection: Workflow identity/name, approved configuration, archive state, configuration revision, digest, and approval time. Unknown internal fields, recognized secrets, and local paths are rejected. The provider interface is owner-scoped and supports idempotent compare-and-set writes, tombstone/non-resurrection semantics, bounded stable pagination, and invalid-cursor recovery through authoritative refresh. A deterministic in-memory provider proves those contract semantics, owner isolation, revision conflicts, operation replay, deletion non-resurrection, and upload/download/conflict planning without network access or task dispatch. It does not prove storage durability across process restarts.

The Supabase adapter, migration, encrypted-session fallback policy, owner-partitioned local synchronization ledger, durable pending-operation journal, desktop IPC, Settings states, owner-specific portable export, explicit cloud-copy removal, and account-deletion function are implemented. The ledger separates device-local identity from owner-scoped cloud identity, so account switching cannot transfer ownership and colliding identities from different owners remain distinct locally. Deterministic application tests cover two devices, offline edits/deletion, restart, response uncertainty, explicit account switching, signed-out creation, owner identity collisions, in-flight identity fencing, remote deletion and authoritative absence, provider outage, conditional revisions, durable idempotency, and portable-field rejection. `pnpm test:workflow-sync:postgres` executes the real migration in an isolated native PostgreSQL cluster under non-superuser/non-`BYPASSRLS` client roles and proves grants, SELECT/INSERT/UPDATE/DELETE RLS, cross-owner denial, direct RPC validation, first-create concurrency, update CAS, server digest/timing, stable pagination, purge/cursor invalidation/non-resurrection, and account deletion. The harness simulates Supabase `auth.uid()` through a request claim setting; live JWT/OAuth/gateway and packaged-client behavior remain unqualified. The local task database remains the sole source of task/execution truth.

## Remaining deployment qualification

1. Provision the Frankfurt Supabase Free project, enable Google and email OTP, apply the migration, and deploy the account-deletion function.
2. Exercise owner-denial, two real devices, offline edits, stale writes after deletion, account switch, outage/inactivity recovery, export, and account deletion against that isolated project.
3. Do not describe the boundary as production-qualified until those deployed checks pass.
